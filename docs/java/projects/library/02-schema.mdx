## 这一步要完成什么

前置：[能启动项目并创建图书](./01-setup.mdx)。打开 `src/main/resources/schema.sql`，本课要能解释为什么需要两张表，以及哪些规则适合由数据库直接保护。

## 第一步：从业务对象推导表

Book 保存“这本书是什么”和“现在可借多少册”；Loan 保存“某次借阅是谁、何时发生、何时归还”。一本书可以被借多次，一次借阅只属于一本书，因此是图书到借阅的一对多关系。

| 数据 | 保存位置 | 不应混淆的概念 |
| --- | --- | --- |
| title、author | books | 书目信息 |
| total_copies | books | 这条书目的总册数 |
| available_copies | books | 当前仍可借出的册数 |
| book_id、borrower | loans | 一次借阅的关联与人员文本 |
| created_at、returned_at | loans | 借出时间、归还时间 |

不要只在图书上保存一个 borrower 字段。一本书有多册，也有多次历史，单个字段无法表达同时借给多个人与之后归还的情况。

## 第二步：读懂数据库约束

schema.sql 中的关键规则包括主键、NOT NULL、外键和 CHECK。下面是概念片段，具体建表以下载项目的完整 schema.sql 为准，不要把它当第二份表定义重复执行：

```sql
CHECK (available_copies >= 0 AND available_copies <= total_copies)
```

这条约束保护库存范围。请求校验先给用户友好的错误，业务服务表达借还规则，数据库约束作为存储层的最后一道一致性检查，三者各有作用。

主键由数据库生成，不能在应用中用“当前最大 id 加 1”分配。并发创建时两个请求可能看见同一个最大值，而数据库生成机制能正确协调。

外键确保借阅关联的图书真实存在。项目还在删除入口主动检查借阅历史并返回 409，避免用户只看到难以理解的数据库异常。

## 第三步：状态通过时间字段表达

未归还记录的 returned_at 为 null，归还时写入时间。前端以此判断是否展示归还按钮，后端以此判断是否允许再次归还。不要仅靠页面按钮隐藏来保护规则，任何调用者都能直接发 HTTP 请求。

响应时间使用 UTC 字符串。页面显示时可转换成用户本地时间；保存的时间点与用户看到的时区格式是两个问题。测试应检查是否有时间及状态是否变化，不要把运行当下的时间写死为固定预期。

## 第四步：连接配置决定数据生命周期

查看 `src/main/resources/application.properties` 的 H2 连接，应用使用 `jdbc:h2:file:./data/library`。路径中的点表示进程工作目录，data 文件夹下的数据库会跨进程重启保留。

测试改为内存连接，不写入该文件。运行两份应用时，应使用不同文件路径，否则 H2 文件锁可能阻止第二个进程启动。

`CREATE TABLE IF NOT EXISTS` 能让建表重复执行，**不能完成旧表迁移**。把源码中的列长度从 80 改成 40，不会自动安全地处理旧数据库里的长标题。正式工程需要明确迁移脚本与旧数据处理策略。

## 第五步：思考冗余库存的代价

理论上可以通过总册数减去未归还记录数计算可借数量。项目直接保存 available_copies，使借出时可以执行条件更新，避免先查询再更新的竞争窗口；代价是每次借还都必须维护它与历史一致。

所以必须把库存变化和记录变化放进同一事务，而不能在不同 HTTP 请求中分别完成。下一步先学习图书查询，之后专门验证借还事务。

## 动手任务

假设总册数是 2，连续借出两次、归还一次，分别写出 available_copies 和未归还记录数。然后说明第三次借出失败时数据库应该留下什么变化。

<details>
<summary>参考答案与验收</summary>

初始库存 2、未归还 0；第一次后 1、1；第二次后 0、2；归还一次后 1、1。若在库存 0 时尝试第三次借出，应返回 409，库存保持 0，也不能新增借阅记录。两项都要检查，只看错误状态不足以证明事务正确。

</details>
